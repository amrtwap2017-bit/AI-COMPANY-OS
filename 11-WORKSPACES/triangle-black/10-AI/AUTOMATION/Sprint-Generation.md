# Automated Sprint Generation

## Overview

Sprint generation automates the creation of sprint plans from the prioritized task backlog. The Program Manager AI builds sprints that respect velocity constraints, dependency ordering, and sprint goals while maximizing delivered value.

## Sprint Scoping

### Backlog Ingestion

The generation process begins by ingesting:

- All unassigned, ready-to-implement tasks from `BACKLOG.md`
- Carry-over tasks from the previous incomplete sprint
- High-priority (P0/P1) tasks added since last sprint
- Technical debt tasks flagged by the Code Review AI
- Bug fixes triaged as sprint-necessary

### Scoping Algorithm

Sprint scoping follows a value-optimization approach:

1. **Filter**: Include only tasks with status `ready` and all dependencies resolved
2. **Prioritize**: Sort by priority (P0→P3), then by business value score, then by dependency order
3. **Select**: Add tasks to sprint in priority order until velocity capacity is reached
4. **Adjust**: If adding a task would exceed capacity, swap with lower-value tasks of similar size
5. **Finalize**: Lock sprint scope and generate sprint goal

### Carry-Over Handling

Incomplete tasks from the previous sprint receive priority placement:

- Tasks at 50-99% completion are placed with 24% capacity reservation
- Tasks at 1-49% completion are re-estimated and compete with new tasks
- Tasks at 0% (not started) are evaluated: if still relevant, re-prioritized; otherwise returned to backlog

## Velocity-Based Capacity Planning

### Velocity Calculation

Team velocity is calculated from historical sprint data:

```
velocity_rolling_avg = MEAN(last 3 sprints: total_completed_story_points)
velocity_weighted = 0.5 * last_sprint + 0.3 * second_last + 0.2 * third_last
velocity_capacity = velocity_rolling_avg * capacity_factor
```

Where `capacity_factor` accounts for:

| Factor | Adjustment | Description |
|--------|-----------|-------------|
| Sprint length | ±0-15% | Shortened sprints reduce velocity |
| Team composition | ±0-20% | Role changes affect throughput |
| Holiday/leave | -10-30% | Reduced availability days |
| Technical debt | -5-15% | Higher debt reduces effective velocity |
| New team member | -10-25% | Ramp-up overhead |

### Capacity Budgeting

Sprint capacity is allocated across work categories:

| Category | Allocation | Description |
|----------|-----------|-------------|
| Feature development | 55-70% | New functionality tasks |
| Bug fixes | 10-15% | In-sprint bug resolution |
| Technical debt | 10-15% | Refactoring and debt reduction |
| Testing/QA | 5-10% | Test automation, E2E testing |
| Documentation | 5% | Documentation updates |
| Buffer | 5-10% | Unplanned work, spillover |

### Overtime Protection

The system enforces a velocity ceiling of 120% of the rolling average. Sprints exceeding this trigger:

1. A warning notification to the pipeline orchestrator
2. Automatic burstification (moving lower-priority items to next sprint)
3. Escalation for human review if ceiling exceeded by more than 20%

## Sprint Goal Formulation

### Goal Structure

Each sprint receives a structured goal statement:

```
Sprint {number} Goal: {verb} {target} to achieve {outcome}
```

Examples:
- Sprint 12 Goal: Implement user authentication flows to enable secure login and registration
- Sprint 14 Goal: Deploy monitoring infrastructure to achieve production observability

### Goal Generation Rules

Sprint goals are generated by:

1. Identifying the highest-value theme among selected tasks
2. Extracting the common business outcome from tasks in that theme
3. Formulating as a SMART goal:
   - **S**pecific: Clear, unambiguous target
   - **M**easurable: Success criteria quantifiable
   - **A**chievable: Within sprint scope and velocity
   - **R**elevant: Aligned with program objectives
   - **T**ime-bound: Deliverable within sprint duration

### Goal Types

| Goal Type | Pattern | When Used |
|-----------|---------|-----------|
| Feature delivery | "Ship {feature} to enable {capability}" | Feature-focused sprint |
| Capability expansion | "Extend {system} to support {use case}" | Enhancement sprint |
| Foundation building | "Establish {infrastructure} for {future need}" | Infrastructure sprint |
| Quality improvement | "Reduce {metric} to {target} by {action}" | Debt/bug sprint |
| Milestone | "Achieve {milestone} readiness for {event}" | Milestone-targeted sprint |

## Sprint Backlog Creation

### Backlog Structure

The generated sprint backlog includes:

```yaml
sprint:
  number: {next-number}
  goal: "{sprint-goal-formulation}"
  duration_days: 14
  start_date: "{YYYY-MM-DD}"
  end_date: "{YYYY-MM-DD}"
  velocity:
    planned: {total-story-points}
    capacity: {available-hours}
    buffer: {buffer-hours}
  tasks:
    - id: TSK-{id}
      title: "{task-title}"
      owner: "{ai-role}"
      points: {story-points}
      status: "planned"
      dependencies: []
  goals:
    primary: "{primary-goal}"
    secondary:
      - "{secondary-goal}"
  risks:
    - "{risk-description}"
```

### Task Ordering Within Sprint

Tasks within the sprint backlog are ordered by:

1. **Dependency-first**: All tasks a task depends on appear before it
2. **Priority-within-layer**: Higher-priority tasks first within same architectural layer
3. **Frontload uncertainty**: High-uncertainty tasks early to surface blockers
4. **Parallelization**: Independent tasks placed for maximum parallel execution

### Sprint Backlog Validation

Before finalizing, the sprint backlog is validated:

- Capacity check: Total story points ≤ velocity_capacity (with buffer)
- Dependency check: All intra-sprint dependencies are satisfiable
- Resource check: No single role assigned more than their capacity
- Continuity check: No more than 30% of tasks are carry-over
- Goal alignment: At least 60% of sprint points align with sprint goal

### Finalization and Output

The finalized sprint plan is written to `SPRINT-{number}-PLAN.md` in the program workspace, containing:

- Sprint overview with dates, capacity, and team composition
- Sprint goal and success criteria
- Task backlog with ordering
- Risk register for the sprint
- Definition of sprint done (sprint-level quality gates)

The sprint is also registered in the program tracking system with `status: active`.
