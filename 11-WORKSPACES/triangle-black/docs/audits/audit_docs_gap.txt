# 🏨 Triangle Black: Architectural Overview & Implementation Guide

## 1. Strategic Foundation
*   **Domain:** Hospitality Operations (Properties, Reservations, Billing, Housekeeping).
*   **Core Philosophy:** Domain-Driven Design (DDD) with clear Bounded Contexts to prevent context switching and ensure modularity.
*   **Ubiquitous Language:** Strict adherence to terms like `Property`, `Unit`, `Folio`, and `Rate Plan` ensures developers share a common mental model.

## 2. Technology Stack Summary
The system is built for rapid development, strong typing, and multi-tenancy using a unified TypeScript ecosystem.

| Layer | Choice | Key Constraint/Feature |
| :--- | :--- | :--- |
| **Frontend** | Next.js (App Router) | SSR for SEO; BFF API routes to avoid CORS; Middleware for tenant resolution. |
| **Backend** | NestJS | Modular architecture mirroring DDD contexts; Built-in DI & Event Bus. |
| **Database** | PostgreSQL 16+ | **Schema-per-tenant** isolation (Primary Strategy); JSONB flexibility. |
| **ORM** | Prisma | Type-safe queries; Declarative schema migrations per tenant. |
| **Auth** | JWT + Refresh Tokens | Stateless access tokens (15m) + Opaque/DB-stored refresh tokens (7d). |
| **Storage** | Local Disk (V1) → S3 Compatible (V2+) | Abstraction layer allows easy migration; Nginx serves static files. |

## 3. Critical Architectural Patterns

### A. Multi-Tenancy Strategy: Schema Per Tenant
This is the most significant architectural decision for data isolation and security in V1.
*   **Structure:** One database (`triangle_black`) containing multiple schemas (e.g., `tenant_abc`, `public`).
*   **Isolation Mechanism:** The application uses a middleware to set `SET search_path` based on the tenant ID extracted from headers or subdomains before executing any query.
*   **Benefit:** Hard isolation prevents accidental data leakage; backups can be scripted per-schema (`pg_dump schema_name`).
*   **Risk Mitigation:** Connection pooling (PgBouncer) must handle many schemas carefully to avoid exhaustion under high load.

### B. API Design: RESTful with URL Versioning
*   **Standard:** `GET /api/v1/{resource}`.
*   **Tenant Context:** Enforced via headers (`X-Tenant-Id`) or subdomains, not query parameters (to keep URLs clean).
*   **Versioning:** Explicit `/v1` prefix allows safe evolution of the API without breaking existing clients immediately.

### C. Domain Boundaries & Communication
*   **Bounded Contexts:** `Reservation Management`, `Billing`, `Property Config`, and `Housekeeping`.
*   **Internal Comm:** NestJS's built-in Event Bus (`@nestjs/event-emitter`) is preferred for cross-module domain events (e.g., "Booking Confirmed" triggering a Housekeeping task).
*   **External Integrations:** REST API exposes capabilities to OTAs, PMS systems, and mobile apps.

## 4. Operational Considerations & Risks

### ⚠️ Scalability Warning: Schema Per Tenant
While excellent for V1 (single VPS), this approach has limits as the tenant count grows beyond ~50-100 active schemas per database instance.
*   **Connection Pool Strain:** Each schema consumes a connection slot in PgBouncer. If you have 200 tenants, you need 200+ connections unless using advanced pooling strategies (like `pgbouncer-pool` or custom logic).
*   **Migration Overhead:** Running migrations per-schema can become slow if many schemas are updated simultaneously during a release cycle.
    *   *Recommendation:* Consider batching schema updates or moving to "Row-Level Security" + Single Schema for V2+ once tenant count exceeds capacity limits.

### ⚠️ TypeScript Ecosystem Dependency
*   **Single Point of Failure:** The entire stack relies on the maturity and stability of the TypeScript ecosystem (React, NestJS, Prisma). Any major breaking change in these core libraries will impact all layers simultaneously.
*   **Performance Ceiling:** Node.js is not ideal for CPU-intensive tasks (e.g., complex billing calculations or heavy image processing). These should be offloaded to worker threads or external services where possible.

### ⚠️ Database Backup Granularity
*   PostgreSQL backups are typically per-database, not per-schema by default.
*   **Action Required:** Implement a custom backup script that iterates through schemas and dumps them individually (`pg_dump -s tenant_abc`) to ensure true tenant-level recovery points without restoring the whole DB.

## 5. Immediate Next Steps for Development Team

1.  **Setup Prisma Schema Template:** Create a base schema file with `tenantId` as a required field on all tables, but logically separated into different schemas in production (or use a single schema with RLS if you decide to pivot later).
2.  **Implement Tenant Resolver Middleware:** Ensure this runs before any controller logic or database query to set the search path correctly.
3.  **Define Domain Events:** Map out which events trigger cross-context actions (e.g., `ReservationCreated` → `HousekeepingTaskScheduled`).
4.  **Draft Migration Scripts:** Write a utility script for backing up/restoring individual schemas, as this is critical for tenant data protection compliance.

This architecture provides a solid foundation for launching Triangle Black quickly while maintaining the structural integrity needed to handle complex hospitality workflows and multi-tenant requirements.
